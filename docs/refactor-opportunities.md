# Refactor Opportunities Report

_Generated by the repo-cleanup-autopilot skill on 2026-06-08. Branch: `main`._

## 1. Repository Overview

A React + TypeScript + Vite single-page poker range trainer. Source is cleanly
layered, matching `CLAUDE.md`'s rules:

- `src/domain/` — pure poker/training logic (hands, range math, notation,
  practice scoring, spaced repetition, drills). No React, no storage.
- `src/storage/` — `localStorage`-backed persistence, one module per concern,
  each side-effect-only behind a small exported API and a versioned key.
- `src/components/` — React UI.
- `src/types/` — shared domain types.

~5,080 lines of non-test source across 40 files; ~8,620 lines of tests. Test
coverage is strong: **671 tests in 38 files, all green.** Lint and build are
both clean.

## 2. Current Quality Summary

The codebase is in good shape. Documentation is thorough, naming is consistent,
functions are small and pure where it counts, and the domain/UI/storage
boundaries are respected. Notable positives:

- No `TODO`/`FIXME`/`HACK` markers.
- No stray `console`/`debugger` statements.
- No genuinely dead exports (the three exports not imported cross-file —
  `HandCategory`, `HeatLevel`, `DAY_MS` — are each return types of exported
  functions or used internally, so they are intentional, not dead).
- Lint passes with zero warnings.

The main quality issue is **mechanical duplication in the storage layer**, where
five sibling modules grew by being copied from one another (their own docstrings
say so: "Mirrors `practiceStatsStorage.ts`", "Mirrors `handAccuracyRate`"). This
is exactly the low-risk, high-confidence cleanup this pass targets.

## 3. Highest-Value Refactor Opportunities

### Opportunity A — Deduplicate `isNonNegativeFinite` across storage modules

- **Location/files:** `src/storage/practiceStatsStorage.ts`,
  `reviewStateStorage.ts`, `sessionHistoryStorage.ts`, `actionAccuracyStorage.ts`,
  `handAccuracyStorage.ts`.
- **Problem:** The exact predicate
  `typeof value === 'number' && Number.isFinite(value) && value >= 0` is copied
  verbatim into five files.
- **Why it matters:** Five copies of one validation rule drift independently; a
  fix or tightening has to be made five times.
- **Suggested refactor:** Add `src/storage/storageHelpers.ts` exporting
  `isNonNegativeFinite`; import it in all five modules; delete the local copies.
- **Risk level:** Low (pure, verbatim, behavior-identical).
- **Expected benefit:** Single source of truth; ~5 fewer duplicated definitions.
- **Suggested validation:** `npm run lint && npm run test:run && npm run build`.
- **Dependency ordering:** Do first; Opportunity B extends the same new file.
- **Autopilot status:** Implemented

### Opportunity B — Deduplicate the `localStorage` read + JSON.parse boilerplate

- **Location/files:** all six storage loaders: the five above plus
  `src/storage/rangeStorage.ts`.
- **Problem:** Every loader repeats the same opening:
  `getItem(KEY)` → `null` check → `JSON.parse` inside `try/catch` →
  `return {}`/`[]` on corrupt JSON.
- **Why it matters:** ~6 lines × 6 files of identical IO/error-handling
  boilerplate, obscuring the part that actually differs (the per-shape
  validation).
- **Suggested refactor:** Add a `readJson(key): unknown` helper to
  `storageHelpers.ts` that returns the parsed value or `undefined` on miss/corrupt.
  Each loader keeps its own shape check (`Array.isArray` for ranges; non-null
  non-array object for the maps).
- **Risk level:** Low (behavior-identical; strong existing corrupt-JSON tests).
- **Expected benefit:** Each loader drops to one line of IO before its real logic.
- **Suggested validation:** `npm run lint && npm run test:run && npm run build`.
- **Dependency ordering:** After A (same file).
- **Autopilot status:** Implemented

### Opportunity C — Extract a pure `accuracyPercentage(correct, total)` primitive

- **Location/files:** `src/domain/practiceStats.ts:13`, `src/domain/practice.ts:72`,
  `src/domain/practice.ts:138`, `src/domain/actionRange.ts:101`.
- **Problem:** The guarded ratio `total === 0 ? 0 : (correct / total) * 100`
  appears in four domain helpers (`actionAccuracyRate` even documents that it
  "Mirrors `handAccuracyRate`").
- **Why it matters:** The "never divide by zero, scale to 0–100" convention is
  re-encoded at each site; one source of truth makes the convention explicit and
  testable in isolation.
- **Note on prior intent:** A comment in `sortRangesByAccuracy`
  (`rangeLibrary.ts:222`) keeps its division inline "so the helper stays decoupled
  from the fuller `RangePracticeStats` shape." A **two-number** primitive
  sidesteps that concern entirely — callers still extract their own fields — so it
  does not contradict that decision. `sortRangesByAccuracy` itself is left alone
  (its zero case returns a `-1` sentinel, not `0`, so the semantics differ).
- **Suggested refactor:** Add `src/domain/accuracy.ts` exporting
  `accuracyPercentage(correct, total)`; call it from the four helpers above.
- **Risk level:** Low–Medium (well-tested, but spans three domain files).
- **Expected benefit:** One tested definition of the accuracy convention.
- **Suggested validation:** `npm run lint && npm run test:run && npm run build`.
- **Dependency ordering:** Independent of A/B.
- **Autopilot status:** Implemented

### Opportunity D — Share the enum-membership guard between storage modules

- **Location/files:** `src/storage/rangeStorage.ts` (`asMember`),
  `src/storage/actionAccuracyStorage.ts` (`isRangeAction`).
- **Problem:** `isRangeAction(v)` is just `asMember(RANGE_ACTIONS, v) !== undefined`;
  the membership-check logic is written twice.
- **Why it matters:** Minor duplication of a validation primitive.
- **Suggested refactor:** Move `asMember` into `storageHelpers.ts` and define
  `isRangeAction` in terms of it (or call `asMember` directly).
- **Risk level:** Low.
- **Expected benefit:** One membership-check primitive.
- **Suggested validation:** `npm run lint && npm run test:run && npm run build`.
- **Dependency ordering:** After A (same file).
- **Autopilot status:** Implemented

## 5. Larger Refactors

- **`src/App.tsx` (641 lines)** is the app's orchestrator: routing between
  views, owning saved-range state, and wiring every feature. Splitting view
  state or extracting a router/reducer is plausible but **behavior-sensitive and
  product-shaped** — out of scope for an autonomous low-risk pass.
- **`src/components/RangeLibrary.tsx` (432 lines)** combines filtering, sorting,
  and list rendering. Could be decomposed, but it is UI-behavior-heavy; defer.

## 6. Things Not Worth Refactoring Yet

- `HandCategory`, `HeatLevel`, `DAY_MS` exports — referenced as return types or
  used internally; not dead. Un-exporting would reduce API ergonomics for no real
  gain. Leave them.
- `RangePerformance.tsx:139` computes a percentage **without** a zero guard on
  purpose (a recorded session always has `totalQuestions > 0`); not a candidate
  for the guarded `accuracyPercentage` primitive.
- `ActionQuiz.tsx:86` could call `Math.round(accuracyPercentage(...))`, but that
  pulls a domain helper into a component for a single site; skipped to keep the
  primitive's first use inside the domain layer.

## 7. Suggested Refactor Sequence

2. B — extract `readJson` (extends `storageHelpers.ts`).
3. D — share `asMember`/`isRangeAction` (extends `storageHelpers.ts`).
4. C — extract `accuracyPercentage` (independent domain change).

and it establishes the shared `storageHelpers.ts` that B and D build on.
